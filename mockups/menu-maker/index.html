01

Why the same chat — and not a "menu mode"

The product's whole identity is one conversation with a designer who figures out what you need. A restaurant owner shouldn't have to know that menus are a separate feature before they type. The brain already routes by content type (the FirstThen spec designed exactly this seam) — a menu is the second document type flowing through the same pipe, not a second pipe.

One chat, two document types Recommended

  • Zero mode-picking. "I need a menu for my restaurant" just works, mid-conversation, same composer. The interpreter detects menu intent and switches to the MenuSpec path.
  • All the expensive machinery is reused: quota gating + paywall, the 13-language row, SSE streaming, chat history, onboarding, reference edits, annotate-to-edit.
  • What differs is cards, not conversation: item-table review card, paged results card, PDF row. Three new SwiftUI cards on the existing chat scroll.
  • Cross-sell for free. A flyer customer who mentions a menu gets one; a menu customer's "make me a Friday special flyer" already works.

A separate "Menu maker" chat Rejected

  • Forks everything: a second entry point, second gating path, second history list, second onboarding to explain — for the same underlying brain.
  • Demands discovery. The user must find the mode before typing; a menu request typed into the normal chat would dead-end or deflect.
  • Punishes mixed needs. Restaurants need flyers AND menus; two silos mean two conversations about one business.
  • Buys nothing. The only upside — prompt isolation — already exists inside the interpreter's per-content-type branch.
02

The trick that makes menus possible at all

The finding's three walls (typos, no pages, no print) all come from one root: the image model paints every letter. Path B splits the job — and every wall falls at once.

Nano Banana · once per menu

The AI paints the stage

One generation renders the theme: background texture, header art, the restaurant's vibe — with reserved clear zones where text will live (same "keep this area clean" clause the QR feature already uses). Reused across every page for perfect consistency.

+
Headless Chrome · every word

Code sets the type

HTML/CSS templates typeset the sections, items and prices onto the stage — the same engine the carousel export scripts already trust. World-class line-breaking, full RTL shaping for all 13 languages, true A4/Letter dimensions, and --print-to-pdf makes the print file nearly free.

What this buys: a wrong price becomes impossible, "change the biryani to $14.99" is a free 3-second re-typeset instead of a minute-long generation, pages are unlimited at one generation's cost, and menus print for real. The same compositing layer is what Noor needs for Qur'anic text and FirstThen wants for props — build once, three products inherit it.

04

What each layer needs (Path B build shape)

Matches the finding's four phases. The chat, gating, paywall, language machinery and edit paths are reused untouched — this is the delta only.

Engine

  • MenuSpec content type: restaurant info + sections of {name, description, price, tags} — the FirstThen vertical seam.
  • Interpreter branch + a real restaurant rubric (today it falls to GENERIC).
  • Background-mode prompt: theme with reserved text zones (QR keep-clear clause as precedent).
  • HTML menu templates + headless Chrome typesetting in the container (~1 GB memory bump); PNG pages + one PDF via print-to-pdf.
  • Composite behind the existing _with_qr-style seam, fail-open.

Wire

  • Page-labeled results (page index + label on concepts, or a new pages event).
  • Per-page SSE frames — never 6 full-res pages in one buffered frame.
  • Page-scoped edit actions so "edit page 2" has a wire representation.
  • Menu review payload: the item table with per-row flags (unreadable price etc.).

iOS

  • Menu review card (item table, inline price editing, section drag).
  • Menu group in SwiftData: groupID + pageIndex on SavedFlyer — CloudKit Production schema deploy before release.
  • Paged result card + paged gallery detail (swipe, thumbnails).
  • PDF share (surface the engine's PDF; no client-side PDF math).
  • Stacked group card in My Flyers with page-count badge.
05

The four open decisions — with my picks

1 · How ambitious?
Pick: real menu maker (Path B)

The single-page "menu board" stopgap keeps the typo risk on the exact category where a typo is a wrong price, and it would be another point patch. If menus fit on one page, Path B simply produces a one-page menu — the small case falls out of the real build for free.

2 · What does a menu cost?
Pick: 1 menu = 1 unit, text edits free

Create (3 themes) = 1 quota unit — identical to a flyer, easy to explain. Item/price edits are free (they cost us nothing). A design re-theme = 1 unit. Economics are better than flyers: one themed generation serves unlimited pages.

3 · PDF at launch?
Pick: yes — must-have

Menus are the one category that prints at a shop. With Chrome typesetting, the PDF is nearly free to produce — shipping without it would discard the strongest differentiator of the whole approach.

4 · Chromium in the engine container?
Pick: yes — bless it

The carousel export scripts already trust headless Chrome for pixel-exact rendering locally. It buys world-class text layout and RTL shaping for all 13 languages — the alternative (hand-rolling line-breaking and Arabic shaping in Pillow) is the hard 20% forever. Cost: bigger image, ~1 GB memory bump on Cloud Run.
